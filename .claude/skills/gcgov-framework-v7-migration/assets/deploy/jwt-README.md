# JWT signing keys

The keys are not stored here. They are secrets, they are gitignored in the application repository,
and they are therefore absent from every built image. A container with no keys cannot authenticate
anyone.

## Generate them

**Run on your workstation, in the application repository's checkout**, once per application:

```bash
vendor/bin/gf cert:generate-auth
```

The command writes `guids.json`, one `private-<guid>.pem` and one `public-<guid>.pem`.

## Add them to the secrets file

**Run on your workstation.** Open this application's encrypted file and add each file under a
`JWT/` key prefix. Provisioning writes them to `/etc/gcgov/secrets/<app>/jwt/`:

```bash
sops zones/<zone>/apps/<app>/secrets.sops.yaml
```

```yaml
JWT/guids.json: |
    [
        "<guid>"
    ]
JWT/private-<guid>.pem: |
    -----BEGIN PRIVATE KEY-----
    ...
JWT/public-<guid>.pem: |
    -----BEGIN PUBLIC KEY-----
    ...
```

`guids.json` is a JSON array of the GUIDs, exactly as `gf cert:generate-auth` writes it: square
brackets, not braces. Copy the file as generated. The framework decodes it and expects an array.
`{ "<guid>", ... }` is not valid JSON, so it finds no keys at all. Every sign-in then fails, and
`/api/health/ready` returns 503 with "no usable JWT signing keys".

Then provision and restart, following [rotate-a-secret.md](../../../../../docs/runbooks/rotate-a-secret.md),
step 3.

## Rules

A secret key containing `/` becomes a subdirectory. Anything else becomes a file directly under
`/etc/gcgov/secrets/<app>/`. Do not put the keys on the host by hand. Provisioning syncs that
directory with `--delete`, so a hand-placed file is removed by the next run, and authentication
breaks at the following container restart with nothing to point at the cause.

Filenames must be lowercase. Provisioning lowercases every secret key it writes, and the host
filesystem is case-sensitive. A `private-<GUID>.pem` whose GUID carries uppercase letters lands as
a lowercase file while `guids.json` still names the uppercase spelling, and the framework, which
looks files up by that spelling, finds no keys at all. Current `gf cert:generate-auth` builds emit
lowercase GUIDs. Keys generated by an older build on Windows, where GUIDs come out uppercase,
should be regenerated, or have both the filenames and the `guids.json` entries lowercased, before
they are added here.

The compose file must also set `APP_JWT_KEY_PATH` to the mounted directory. Mounting the keys is
only half of it. Without that variable the framework looks in `{root}/srv/jwtCertificates`, which no
image contains, and every authenticated route throws while `/api/health` keeps reporting the
container healthy.

Every replica must hold the same set. Regenerating them signs every user out, so the framework
supports several keys at once through `guids.json`. Rotate by adding a key, not by replacing the
set.
